# TimeLedger（时间记账）

Android 原生「时间管理 / 时间记账」App。

核心不是让用户手动记录一天，而是：

> 通过「目标 → 计划 → 系统感知 → 时间轴 → 用户确认 → 复盘」自动还原用户一天的时间使用情况。

产品核心价值：**让用户少记录，却更清楚自己一天是怎么度过的。**

**模块 20：第一次真机使用后的修正 —— 已完成（有前后对比数据）**

装到手机上用了一天之后，用户反馈两条：「抓取的时间不太准，很多没记上」和「太碎，一堆待确认」。
把数据库拉下来一算，问题比预想的具体，也发现了我自己的一条设计漏洞。

| 改了什么 | 依据（真机数据） | 结果 |
|---|---|---|
| **排除「不是用户在使用」的包**：桌面、系统界面、输入法，以及**所有没有桌面入口的系统组件** | 30 小时里桌面出现 559 次；归类页里躺着 47 个待归类，混着权限管理、权限控制器、软件包安装程序、阅图锁屏 | 这些不再出现在时间轴和归类页里 |
| **离开 30 秒内回来算同一段**（并吃掉中间的插曲） | 2731 段里 1625 段的下一段就是同一个 App；2407 段碎片短于 5 秒 | 系统记录总时长 3h50m → 5h37m（找回 1h47m） |
| **未归类不再逐条确认**，改由归类页按 App 问一次 | 47 条待确认，77% 短于 5 分钟 —— 用户还没归类过任何 App，于是每条都在问他 | 待确认 **47 → 0** |
| **不打扰用时很少的 App**（< 10 分钟收进「另有 N 个」，不催） | 47 个待归类里 24 个用时不到 1 分钟（天气 0 分钟、信息 0.1 分钟…） | 归类页只剩 11 个值得处理的 |
| **时间轴折叠零碎段**（< 5 分钟的系统段收成一行，可展开） | 某一天 87 条记录里 70 条短于 5 分钟 —— 87 行罗列出来看不出「这一天是怎么过的」 | 时间轴 87 行 → 18 行 |

**改造前后对比**（`tools/compare_records.py`，只读 App 实际写入的记录）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 系统记录条数 | 47 | 87 |
| 待确认条数 | **47** | **0** |
| 未归类条数 / 时长 | 47 条 / **3h50m** | 1 条 / **1m** |
| 系统记录总时长 | 3h50m | **5h37m** |

条数变多**不是退步**：以前大量真实使用因为短于阈值被丢掉了，现在它们被记下来了 ——
总量 +1h47m 才是「偏少」这条抱怨的真正修复。

**排查工具**（在 `tools/`，不参与 App 构建）：
`pull_and_diagnose.ps1`（从手机拉数据库，只读）、`diagnose_usage.py`（事件→会话→记录的定量诊断）、
`compare_records.py`（改造前后对比，只读实际记录）、`selftest_diagnose.py`（诊断工具自己的自测）、
`gap_breakdown.py`（空白里到底是什么：黑屏 / 零碎使用 / 没有数据）、
`threshold_probe.py`（**改门槛之前先量**：每个候选门槛会产出多少条记录、多少时长）。

**模块 24：空白块说清楚自己 + 一天的时间饼图 —— 已完成（有前后对比数据）**

用户看完竖轴之后连着问了两件事：「有些空的没有分类是怎么回事」、
「以及间隔中的时间也没有进行分类，而是直接断开？那不进行分类（熄屏）？」，
外加一个明确的需求「需要一天的时间饼图」。

先把「空」拆开算了一遍（09-12，`tools/gap_breakdown.py`）：竖轴上画出来的空白共 **11h59m**，
里面其实有三类完全不同的东西 ——

| 空白里是什么 | 时长 | 为什么没成为记录 |
|---|---|---|
| 屏幕**熄着**（但每段都不到 5 分钟） | 3h19m | 熄屏门槛 5 分钟太高，被亮屏打断的整段就消失了 |
| **真的在划手机**（每次开 App 都不到 1 分钟） | 4h51m | 会话门槛 60 秒，碎片全被丢掉 |
| 系统**一条事件都没有** | 6h03m | 关机 / ROM 没留那么久的历史，问谁都没用 |

三条改动的依据都是这张表：

| 改了什么 | 依据（真机数据） | 结果 |
|---|---|---|
| **熄屏门槛 5 分钟 → 1 分钟** | 「黑屏 ≥30 秒」10h14m，而「≥5 分钟」只有 6h55m —— 3 小时 19 分被亮屏打断而整段消失 | 记录的熄屏 3h38m → **6h14m**；09-12 的空白块 **8 块 → 4 块** |

最后一条最要紧：**聚合绝不等于丢数据**。块里写的是「这一块里记了多少」（真实之和），
标题写的是**占得最多的那一个**，段数写 `N 段`，展开之后每一条各自占一块、都能点到编辑 ——
用户之前抱怨的「太挤、点不准」与「只有分类没有具体应用」两个问题，在这里同时被解决。

**模块 25：按应用的饼图 —— 已完成（有真机数据）**

## 构建

工具链**就在项目里**，放在 `.toolchain/`（项目因此自成一体：整个目录拷到别的机器就能构建）：

- JDK 21：`.toolchain/jdk-21`（系统默认 JDK 是 26，AGP 不支持，必须显式指定）
- Android SDK：`.toolchain/android-sdk`（platforms 35/36、build-tools 35/36、platform-tools、licenses）

`local.properties` 里的 `sdk.dir` 写的是**相对路径** `.toolchain/android-sdk` ——
所以换机器、换盘符都不用改这一行。它已在 `.gitignore` 里；
`.toolchain/`（800 MB，两万多个文件）同样已忽略：**它是工具，不是源码，不进版本库**。

### ⚠️ 项目路径必须是纯英文

这条踩过坑，写在这里免得再踩一次。

项目曾经放在 `D:\Projects\我的项目\Android\TimeLedger` 下（`我的项目` 是中文），结果：

1. **AGP 直接拒绝构建** —— 报「Your project path contains non-ASCII characters」（b.android.com/95744）；
2. 加上 `android.overridePathCheck=true` 绕过检查后，`assembleDebug` 能过，
   但**单元测试全部 `ClassNotFoundException`**（37 个测试类一个都加载不了）——
   测试 JVM 解析不了带中文的 classpath。试过 `-Dsun.jnu.encoding=UTF-8`，**修不好**。

所以本项目的真实位置是 **`D:\Projects\Android\TimeLedger`**（纯英文）。
在这个路径下，干净构建 + 571 个单元测试全部通过。
`D:\Projects\我的项目\Android\TimeLedger` 是一个**目录联接（junction）**，指向真实位置 ——
浏览代码、看文件都正常，但**别从那里构建，也别用 Android Studio 打开那个路径**，
否则会重新撞上上面第 1、2 条。

### 命令行构建

```powershell
$project = 'D:\Projects\Android\TimeLedger'
$jdk = "$project\.toolchain\jdk-21"
$env:JAVA_HOME = $jdk

# Gradle 本体用的是用户目录里已缓存的发行版（项目里没有 wrapper，见下）
$gradle = (Get-ChildItem "$env:USERPROFILE\.gradle\wrapper\dists\gradle-8.14.3-all" `
    -Recurse -Filter 'gradle.bat' -File | Select-Object -First 1).FullName

& $gradle -p $project --console=plain --no-daemon "-Dorg.gradle.java.home=$jdk" `
    :app:assembleDebug :app:testDebugUnitTest
```

产物：`app/build/outputs/apk/debug/app-debug.apk`

### 为什么项目里没有 gradlew

一般项目会带 Gradle Wrapper（`gradlew` + `gradle-wrapper.jar`），
但 wrapper 的作用是**联网下载**指定版本的 Gradle —— 而本机访问不到 `services.gradle.org`。
放一个必然失败的 `gradlew` 进去，比不放更容易误导人。

所以 Gradle 本体用的是用户目录里已经装好的那份（`~/.gradle/wrapper/dists/gradle-8.14.3-all`）。
要换机器的话，两条路：装一个 Gradle 8.14.3，或者等有网络时用
`gradle wrapper --gradle-version 8.14.3` 生成一个真的 wrapper。

用 Android Studio 打开也是可以的：它自带 JDK 21，会忽略上面的 `JAVA_HOME` 设定。
注意第一次打开时它可能会去索引 `.toolchain/`（两万多个文件，会慢一会儿）——
必要时在 `Settings → Directories` 里把它标记为 Excluded。

### 为什么仓库里放了阿里云镜像

`dl.google.com` 与 `repo1.maven.org` 在国内基本不可达，所以 `settings.gradle.kts` 里
把阿里云镜像放在最前面，`google()` / `mavenCentral()` 作为兜底保留。
在有直连的网络环境下可以把镜像删掉，或者把兜底仓库删掉以避免超时等待。

## 版本组合的选取依据

不是随手挑最新版，每一条配对都是可验证的：

| 组件 | 版本 | 为什么是它 |

## 关键设计决策

这些决定都是「改了会出 bug」的类型，因此集中记在这里。

### 1. 一天从 04:00 开始

`9月12日 = 9月12日 04:00 ~ 9月13日 03:59:59.999`。
凌晨 1 点发生的事算「昨天」，与产品「凌晨 4 点才翻篇」的设定一致。

实现只用 `ZonedDateTime`，**绝不加 86400000 毫秒** —— 夏令时切换日的实际长度是 23 或 25 小时。
`TimeBoundaryTest` 里有对应的用例。

### 2. 记录的归属与统计口径（三层，别混）

这是最容易出错的一处，拆成三层讲：

- **左闭右开** `[start, end)`，全局唯一区间语义（`MillisRange`）。
- **存储不拆分**：跨 4:00 的记录（例如 01:00–08:00 的睡眠）只存**一条**。
  切成两条以后，「这一觉睡了多久」就再也还原不出来了。
- **归属按 `startMillis`**：这条记录算 9月12日 的，用于展示与编辑。
- **统计按窗口裁剪**：算「今日总时长」时必须先把区间裁剪到当天窗口
  （`range.intersect(dayWindow)`）再累加。

  为什么必须裁剪：区间查询是按「有交集」返回的，所以一条跨日记录会同时出现在
  两天的查询结果里。直接相加就会把同一条记录算两次，某一天甚至可能超过 24 小时 ——
  对一个时间记账产品来说这是不可接受的。裁剪天然满足
  「同一条记录在各天之间的分摊之和 = 它的总时长」，不重复也不遗漏。

  另一个必须注意的点：手动记录与系统记录**允许重叠**，所以「今日总时长」不能把原始记录
  直接相加，必须在时间轴按优先级消解之后再统计。

- **零长度记录合法**：`end == start` 表示瞬时事件，用于「只记次数」的目标（今天做了 2 题）。
  区间查询为此在 SQL 里补了特例，否则落在区间起点上的瞬时事件会被漏掉。
  注意这类记录**不构成几何重叠**（`MillisRange.overlaps` 对它是 false，
  因为 `[T,T)` 是空集）——「点在某区间内」和「两区间相交」是两个不同的问题。

  相应的，`MillisRange.overlaps` 的实现直接复用了 `intersect`，
  并有测试逐对枚举区间验证「overlaps 等价于 intersect 非空」，
  防止两套公式各自演化出不一致的判定。

### 3. 来源优先级与「手动记录不可覆盖」

```
MANUAL(3) > MERGED(2) > SYSTEM(1) > SUGGESTED(0)
```

- 所有系统写入（`saveSystemRecord`）都会先查是否与手动记录重叠，重叠即拒绝。
- `replaceSystemGeneratedIn`（重新分析某一天）的删除范围写死在 SQL 里，
  只碰 `SYSTEM` / `SUGGESTED`，**永远不含** `MANUAL` / `MERGED`。
- 用户修改过的系统记录来源变成 `MERGED`；手动记录不会被降级。

### 4. 统计永远现算，不存进度

目标表里**没有任何进度字段**，完成度一律从 `time_records` 现算。
存进度就会有「用户改了历史记录、进度没跟着变」的经典 bug，
而手机端的数据量（一年几千条）现算完全够快。

### 5. 分类/活动只归档不硬删，计划/目标可真删

历史记录依赖分类归属，删掉分类会让往年统计失去口径，因此只能归档。
计划条目与目标不被任何历史记录引用，删掉不影响统计，所以允许真删除。

### 6. 不用外键约束

全库统一不使用 `FOREIGN KEY`：
系统采集可能先落库、后补分类，外键会让这些正常写入失败；
引用完整性改由仓库层校验 + 「只归档不硬删」共同保证。
统一策略比一半表有外键一半没有更好维护。

### 7. 系统采集必须有幂等键

`usage_events.event_key` 与 `time_records.external_key` 是唯一索引，
写入一律 `INSERT OR IGNORE`，靠数据库去重而不是「先查后写」——
后者在补采/重试/并发下有竞态窗口。

**特别注意**：软删除的行**仍然占着** `external_key` 唯一索引。
所以「重新分析某一天」必须先软删旧记录、再按同一幂等键写入，
此时必须走「复活并覆盖」而不是插入 —— 否则新结果会被静默丢弃。
`TimeRecordRepositoryImplTest.re-analysis revives the soft deleted row...` 锁住了这个行为。

### 8. 时间上下文必须注入

业务代码不允许直接 `System.currentTimeMillis()` 或 `ZoneId.systemDefault()`，
统一从 `DayBoundary` 取。否则「跨 4:00 边界」这类用例永远不可复现。

### 9. 数据库迁移

- `exportSchema = true`，schema 导出到 `app/schemas/`（**必须提交**，是写迁移的唯一依据）。
- **绝不使用** `fallbackToDestructiveMigration()`：宁可启动崩溃，也不能静默清空用户历史。
- 新增字段一律带 `defaultValue`，迁移脚本只需 `ALTER TABLE ... ADD COLUMN`。
- 迁移统一注册在 `TimeLedgerDatabase.ALL_MIGRATIONS`，`AppContainer` 自动接上。

### 10. 先消解重叠，再统计

需求三节允许手动记录与系统记录覆盖同一时段，因此**任何时长统计都不能把原始记录直接相加**。
`TimelineResolver` 把一天整理成互不重叠的时间轴：收集所有记录边界点 → 切成基本区间 →
每个区间由覆盖它的最高优先级记录胜出 → 相邻且同一条记录的段合并。

胜出顺序完全确定：来源优先级 → 置信度 → 开始时间早的优先 → 输入下标小的优先。
最后两级用来保证确定性（优先级与置信度都相同时，胜负不能随输入顺序摇摆，
否则同一份数据两次渲染出不同时间轴，用户会以为记录丢了）。

举例说明它挡住了什么错误：用户手写「14:00–15:00 Java」，系统测到「14:30–15:30 Android Studio」。
原始记录相加是 2 小时，实际覆盖只有 1.5 小时 —— 这个差值会直接让「Java 今天学了 1.5 小时」
变成 2 小时，目标完成度跟着虚高。

### 11. 目标完成度的三条口径

- **排除 SUGGESTED**：未确认的推测不换成绩。三种目标类型统一排除，
  否则系统一猜就帮用户达标，目标就失去意义了。其余来源（含系统检测到的真实使用事实）
  都算数 —— 这正是「系统数据能否明显减少用户手动记录」要验证的地方。
- **TIME 按窗口裁剪，COUNT / FREQUENCY 按记录归属整体计入**：
  时长可以按分钟切开，所以跨 4:00 的记录按天窗口裁；
  但计数与次数是**不可分割的原子值** —— 一次健身跨过午夜不该被算成半次，
  所以按记录的 `startMillis` 归属到某一个周期里整体计入。
- **不做目标值折算**：周三新建的「每周 15 小时」，那一周仍按 15 小时考核，
  只把统计窗口裁剪到从周三开始。折算成「本周只剩 5 天所以只要 10 小时」听着聪明，
  但产品上没有任何依据，V1 明确不做。

另外，`calculateAll` 只做**一次**重叠消解，所有目标共用同一条时间轴 ——
这样「学习类合计」与「Java 活动」两个目标的数字天然不会互相矛盾。

### 12. 周目标必须取整周的数据

首页同时显示「今日目标」和「本周目标进度」，而周目标的窗口是周一到下周一。
如果只查「今天」的记录，周目标的数字会偏小，而界面上看不出任何异常，
只会让人以为「我这周学得真少」。

`GoalProgressService` 负责算出「该查哪一段」：取所有适用目标窗口的**并集**，
一次查询取全，再交给计算器现算。界面层因此不需要知道「周目标的窗口有多宽」，
也就不会各自实现一套、各漏各的数据。

这个行为由 `GoalProgressServiceTest` 锁住（周一 5 小时 + 周六 2 小时 = 周目标 7 小时）。

### 13. 逻辑日横跨两个日历日 → 计划展开必须同时看 D 和 D+1

逻辑日 = `当天 04:00 ~ 次日 03:59`，它横跨两个**日历日**。于是：

| 计划条目 | 归属哪一格 |
|---|---|
| 周二 09:00 的课 | 周二 |
| **周三 01:00 的日程** | **周二**（凌晨 4 点才翻篇） |
| 周二 23:30–01:00 的跨夜时段 | 周二（整条，结束时刻落在周三） |
| 周六 03:59 开始的条目 | 周五 |

`PlanBlockExpander` 的做法是：同时看日历日 `D` 与 `D+1` 的候选条目，换算成绝对时刻后
用 `DayBoundary.dayKeyOf` **统一判定归属**，只保留真正属于 `D` 的。
规则只有一处实现（`TimeBoundary`），展开器里不另写「几点算今天」。

**DAO 里刻意不提供「按逻辑日取计划」的 SQL**：那种查询只能匹配一个日历日，
早上的条目必然漏掉或错位，而且 `valid_from/valid_to` 拿哪个日期比也无从判断 ——
加一条「看起来能用」的查询，只会变成第二个、且是错的那个答案来源。
课表就几十条，全部取出在内存里展开，代价可以忽略。

### 14. 结束时刻用挂钟时间推算，不用 `start + 时长`

课表上的「09:00」是**挂钟时间**。`DayBoundary.millisAtMinuteOfDay` 用 `LocalTime`
表达挂钟时刻、再由时区规则解析，**不能**写成 `atStartOfDay().plusMinutes(n)` ——
后者加的是**绝对时长**，夏令时切换日会算错一小时：

> 美东 2026-03-08 当天 02:00 直接跳到 03:00。
> 「00:00 加 210 分钟」得到的是 **04:30**，而挂钟 03:30 才是我们要的答案。

这个 bug 是写计划模块时发现的，`DayBoundaryTest` 里有对应用例把它钉住。

### 15. 计划归属按开始时刻；排课冲突不做消解

跨夜的课程整条属于开始那一天，不会在相邻两天各显示一次。
`PlanBlockExpanderTest` 里有一条不变式测试盯着这件事：两周范围内，
每周重复的条目（含跨夜的那条）都恰好出现 **2 次**。

两门课时间冲突时返回两条，既不做消解也不报错 —— 排课冲突是真实存在的，
应该让用户看见，而不是被系统悄悄丢掉一个。

### 16. 复盘的四个时长必须分清

`DurationBreakdown` 里有四个容易混淆的字段，界面上对应四句不同的话：

| 字段 | 含义 | 界面上的话 |
|---|---|---|
| `coveredMillis` | 窗口内有记录覆盖的时长（含未确认的推测） | 「今天 5h20 有记录」 |
| `pendingMillis` | 其中未确认（`SUGGESTED`）的部分 | 「另有 40 分钟待确认」 |
| `confirmedMillis` | 可以信任的部分（分类分布统计的就是它） | 「学习 5h20」 |
| `unrecordedMillis` | 完全没有记录的时间 | 「有 3 小时没记录」 |

**待确认 ≠ 没记录。** 推测片段确实代表「这段时间有数据」，只是还没经用户确认；
所以它不计入缺口，而是单独汇报。搞混的后果是用户会被要求为同一段时间重复确认两次。

三条恒等式由 `TimelineAggregatorTest` 逐条盯着：

- `confirmed + pending == covered`
- `covered + unrecorded == window`
- **各分类之和 == confirmed**：未分类的记录（系统刚采到、还没推断出归属）单独成桶，
  不能丢 —— 丢了用户就会看到一堆加不起来的数字。

### 17. 「计划 vs 实际」给明细，不给一个百分比

需求十节的例子说得很清楚：计划 19:00–21:00 学 Java，实际是
Android Studio 43 分钟、Chrome 35 分钟、B站 20 分钟。
这三段**全部落在计划时段内**，但只有前两段算「按计划」。

所以 `PlanActualComparison` 同时给出「一致了多少」和「具体是什么」：
光给一个百分比，用户没法据此调整安排；给出明细才能回答「我到底把时间花哪了」。

另外两处刻意的克制：

- 计划**没绑定分类/活动**时（例如只写了「自习」），`matchedMillis` 与 `deviatedMillis`
  都返回 0 —— 不知道计划该是什么，就不假装知道用户是否照做了。
- 一天里没有任何计划时，`planAdherenceRatio` 返回 **0 而不是 100%**，
  避免「什么都没安排 = 完美达成」的错觉。

### 18. 复盘不缓存、不落库

`DayReview` 是每次上游数据变化就重新算出来的只读模型。
用户改掉一条上午的记录，总时长、分类分布、计划达成立刻跟着变，不需要任何失效逻辑。
一整天的数据量（几十条记录）重算成本可以忽略，换来的是「永远不会显示过期数字」。

三路数据（记录 / 计划 / 目标）最终都建立在**同一条** `TimelineResolver` 输出上，
因此「学习类合计」与「计划内学习时长」这两个数字不会互相矛盾。
目标进度直接复用 `GoalProgressService`，不在这里重算一遍口径。

### 19. 统计区间必须对齐 04:00，且窗口由日期列表推导

周统计 = `周一 04:00 ~ 下周一 04:00`，月统计 = `1 日 04:00 ~ 次月 1 日 04:00` ——
与记录的**逻辑日**定义完全一致。如果统计用自然日、记录用逻辑日，
凌晨那几小时会被算进相邻区间，出现「周统计加起来 ≠ 月统计」这种对不上的结果。

`windowFor` 先算出区间内的日期列表，再用 `DayBoundary.daysRange` 得到窗口。
这样「逐日明细拼起来」与「区间汇总」在**构造上**就是同一段时间，
不会因为两处独立算边界而差一小时。两条不变式由测试逐条验证：

- 各天 `confirmedMillis` 之和 == 区间 `confirmedMillis`
- 各天窗口首尾相接、无缝隙无重叠（因此各天 `unrecorded` 之和 == 区间 `unrecorded`）

### 20. 重叠消解整段只做一次

统计先对整个区间做**一次** `TimelineResolver`，再按天裁剪 —— 而不是每天各自消解一遍。
原因：一条跨天的记录在两天里可能分别与不同的记录重叠，
按天独立消解会得出不一致的胜负，跨日统计就自相矛盾了。

### 21. 日均的分母是「区间总天数」，不是「有记录的天数」

用后者会得出荒谬的数字：一个月只记了一天 8 小时，就变成「日均 8 小时」。
日均的意义是「平均每天投入多少」，没记录的日子应该按 0 计入平均。

### 22. 统计模型不为每张图配一个字段

需求要的图表有总时长、分类趋势、目标趋势多种。如果每张图配一个专用序列字段，
模型会迅速膨胀，而且多一张图就要改一次模型。
`RangeStatistics` 只提供两样东西：`days`（每天的完整分布）与 `total`（区间汇总）。
于是「总时长趋势」「Java 的趋势」「娱乐的占比」都能由调用方现取现算。

逐日明细**包含没有记录的日子**（各字段为 0）—— 折线图需要连续的空点，
否则「周二没记录」会被画成「周二和周三连成一条线」，看上去像是连续学习了两天。

另外 `StatisticsPeriod` 刻意**没有 DAY**：单日统计已经由 `DayReview` 提供，
再加一个只会产生第二套「一天怎么统计」的实现。

### 23. 界面能验证的只有「编译」和「映射逻辑」

本机没有模拟器、没有连接设备、也没有 Android Studio 的 Preview，**布局长什么样无法目视确认**。
应对办法是把所有「显示什么」的判断从 Composable 里抽出来，集中到 `HomeStateMapper` 这类纯函数：

- 时间轴取哪几段、每段裁到哪里；
- 缺口按什么排序、最多列几段；
- 跨午夜的区间怎么写；
- 没有目标 / 没有记录 / 完全空白时分别显示什么；
- 目标的排序规则。

这些都有单元测试；Composable 里只剩「把结果画出来」，几乎没有可出错的判断。
**能验证的**：编译通过 + 224 个用例；**不能验证的**：间距、换行、深色模式观感、真机渲染。

### 24. 三个 Tab 不用 navigation-compose

三个 Tab 之间没有参数传递、没有深层链接、也不需要返回栈，一个整数状态就够了。
为此引入整套导航框架属于「为了高级而增加复杂度」（需求十六节第 14 条）。
将来真要做「点日历某天跳到当天详情」这类带参跳转时再引入 ——
那时改造点只有 `TimeLedgerApp.kt` 一个文件。

### 25. 图标与进度条也刻意避开依赖

- 底部导航的三个图标用**自带的矢量图**（`res/drawable`），不引入 `material-icons` 扩展库：
  整个 App 只需要三个图标，为此多背一个依赖（还可能和 BOM 版本对不上）不划算。
- 进度条用两个 `Box` 手写，而不是 Material3 的 `LinearProgressIndicator`：
  后者的 `progress` 参数在近几个版本里从 `Float` 改成了 `() -> Float`，用错版本直接编译失败；
  而这里要的东西很简单，手写既没有版本风险，也能自由控制圆角与颜色。

### 26. 跨午夜的区间必须写「次日」

逻辑日横跨午夜（04:00 ~ 次日 03:59），所以「结束时刻在第二天」是**常态而不是例外**。
只写 `22:00–01:00`，用户根本分不清 01:00 是今天凌晨还是明天凌晨 ——
而这个 App 恰恰以「凌晨 4 点才翻篇」为核心设定，显示错会直接误导人。

`HomeStateMapper` 会比较区间两端的**日历日期**，跨日时写成 `22:00–次日 01:00`，并有测试覆盖。

### 27. 快速添加只问两件事

需求一节要求首页有「快速添加记录按钮」。这里刻意只问：**做了什么**、**多久**。
不填起止时刻，时间从「现在」往前推算。

因为用户刚学完半小时 Java 时，脑子里想的是「我刚学了半小时」，
而不是「14:05 到 14:35」—— 要求他回忆精确起止时刻，正是「低操作成本」原则要消灭的摩擦。
分类也不问：选了活动，分类由仓库自动补全。

### 28. 「某一天」的界面是首页与日历共用的

日历里点某一天看到的详情，和首页看到的「今天」，本质上是同一样东西：
那一天的时长、目标、计划对比、时间轴、缺口（日历多一块分类分布）。
所以状态与排版都是共用的：`DayViewUiState` + `DayViewStateMapper` + `DayViewContent`，
首页只多一个「快速添加」按钮。

各写一份的结果一定是慢慢跑偏 —— 一个补了跨夜文案、另一个漏了缺口排序，
而这类不一致在界面上极难被发现。

### 29. 日历从结构上避免同方向嵌套滚动

日历页是「月份网格 + 选中日详情」共用一个滚动区域。
如果详情直接复用带 `verticalScroll` 的 `DayViewContent`，就会出现**同方向嵌套滚动**，
表现是滚不动或滚起来很怪 —— 而这恰恰是本机（没有模拟器与设备）验证不了的。

所以拆出了不带滚动容器的 `DayViewSections`，整个页面只有一个滚动区域。
**能不赌就不赌**：无法目视验证的部分，尽量用结构约束消除，而不是指望它「大概能跑」。

### 30. 月份翻页先归一到 1 号

直接给「1 月 31 日」加一个月会被日历规则截成 2 月 28 日，再往后翻就变成每月 28 号，锚点一路漂移。
`DayBoundary.shiftMonth` 先归一到当月 1 号再平移，翻页完全可预期，并且有测试盯着（含跨年）。

### 31. 日历格子里的小时向下取整

格子里放不下分钟。向上取整会把「记了 1 小时 5 分」显示成 2h —— 那是虚报。
宁可少报一点也不虚报：1 小时 59 分显示 `1h`，不足一小时显示 `<1h`，
没有记录就干脆不显示（而不是给每一天都糊上一个 `0h`）。

同理，当天没有适用目标时不显示 `0/0`：那看起来像「完成了 0 个目标」，
而实际情况是「这天没有目标」，两者必须区分。

### 32. 界面映射器里的中文是硬编码的（一个明确的取舍）

`DayViewStateMapper` / `CalendarStateMapper` 里的文案（`本月记录`、`未归类`、`记了一笔`）
直接写在代码里，没有放进 `strings.xml`。

原因：它们是**纯 JVM 类**，放资源就得把 `Context` 传进来，
测试也就从纯 JVM 测试退化成需要 Android 环境的测试。
而本机没有设备与模拟器，**「能被测试覆盖」的价值远高于多语言准备**。
本项目是中文单语 App，这个取舍是划算的；真要支持多语言时，
改造点是「给映射器传入一个文案提供者」，而不是散落各处的硬编码。

### 33. 统计页不引入图表库，也不画饼图

需求十三节点名了「饼图 / 环形图、柱状图、折线图」，但同一节也写着「不要为了图表而图表」。
最后这一页是两张**手绘**的图：

- **排行用横向条形列表**：按时长排序的条形比饼图更易读 —— 能直接比较长短，也能在旁边放下文字，
  还不需要为「8 个分类怎么区分颜色」另设计一套色板（颜色直接用分类自己的颜色）。
- **趋势用柱状**：柱子的高低就是投入多少，一眼能看出「哪天断了」。

画出来就是两类 `Box`，因此没有任何图表依赖，也不会有版本兼容问题。
**图的形状由「能不能一眼看出模式」决定，而不是由库里有什么决定。**

### 34. 趋势图的粒度随周期变化

周视图 7 根柱子（按天）、月视图 28~31 根（按天）、**年视图 12 根（按月汇总）**。
年视图如果按天画就是 365 根 —— 既看不清也放不下。
粒度选择本身就是「不要为了图表而图表」的一部分：图的作用是让人看出模式，
而不是把所有数据点都塞进去。

### 35. 「隔几根显示一个标签」由映射器决定

月视图有 30 根柱子，每根只有十来个 dp 宽，标签全显示必然互相挤压或截断，
所以改成每 5 天标一次。这个判断写在 `StatsStateMapper` 里而不是 Composable 里 ——
因为**本机无法目视验证界面**，放在映射器里才能被测试覆盖
（测试直接断言「30 根柱子中恰好 6 根带标签，且是 5/10/15/20/25/30」）。

同理，不显示标签的柱子也占一个固定高度的占位，否则柱子基线会参差不齐 ——
这种只有肉眼才能发现的错位，能靠固定尺寸避免就直接避免。

### 36. 目标完成率按目标自己的周期算

统计页选中的是「周 / 月 / 年」，但目标完成率不硬套这个周期：
日目标按当天算、周目标按本周算、月目标按本月算 ——
「每周 15 小时」的目标在年视图里依然是被按周考核的。
每个目标行都带着自己的周期前缀（今日 / 本周 / 本月），用户不会误读。

### 37. 目标值：界面填小时，领域存秒

需求里的写法是「Java 每天 ≥ 3 小时」，用户脑子里也是这个单位；
而领域模型的 `targetValue` 对 TIME 存的是**秒**（避免小时的小数在累加中丢精度）。

换算放在 `GoalForm` 里而不是界面里，因为**它必须被测试覆盖**：
「3 小时变成 10800 秒」算错了，用户看到的进度会整体差 3600 倍 ——
而界面上「3h」的字样看起来完全正常，肉眼发现不了。

### 38. 表单校验失败的两道防线

`GoalForm.validate` 同时决定两件事：**保存按钮是否可点**，以及保存时的最终校验。
同一套规则，就不会出现「按钮能点、点了才报错」这种体验。

这里有一个容易漏的边界：Kotlin 的 `"NaN".toDoubleOrNull()` 会**成功**返回 NaN，
而 NaN 参与的大小比较全是 false —— 只写 `target <= 0` 会把 NaN 放进领域模型。
所以判定写成 `!target.isFinite() || target <= 0`，并用六种输入覆盖测试
（`""`、`"abc"`、`"0"`、`"-1"`、`"NaN"`、`"Infinity"`）。

### 39. 二级页面不用导航库，也不占常驻 Tab

目标管理从首页目标分组的「管理」进入，用一个整数下标表示「当前显示哪个二级页面」，
不引入 navigation-compose：目前只有「显示哪个」这一种状态，没有参数要传。
将来真需要带参数的深层跳转时，改造点只有 `TimeLedgerApp.kt` 一个文件。

它同时**不占常驻 Tab**：需求里明确说首页是「每日控制中心」、日历是「第二个主 Tab」，
目标管理属于偶尔用到的设置类操作。

### 40. 「取全部」还是「只取未归档」是两个不同的问题

- **显示名称时要用全部**（含已归档）：否则绑定到已归档分类的旧目标会显示成「未指定」，
  用户会以为目标坏了；
- **选择器里要用未归档**：不能让用户把新目标绑到一个已经归档的分类上。

所以 ViewModel 订阅的是全部目录，映射器在构造表单选项时再过滤。
这个区别由测试单独锁住：同一个已归档分类，在列表里名字还在，在选择器里不出现。

### 41. 分类 / 活动的「删除」是归档，界面必须说清楚

数据层刻意不物理删除分类与活动：历史 TimeRecord 依赖它们的归属，真删了，
往年统计就会出现无法归属的时间。所以界面按钮写的是**归档 / 恢复**，
并在提示里说明「历史记录仍能正常显示」—— 否则用户会以为「归档」是没删干净。

### 42. 不编辑的字段也必须原样带回

`CategoryRepository.updateCategory` 是**整体更新**：按传入对象的字段覆盖，
只有 `isBuiltIn` 与 `createdAt` 保留库里的。

于是表单必须把 `isArchived`、`sortOrder`、`iconKey` 一起带上 ——
否则「编辑一次名字」会把分类悄悄改成「未归档、排序归零」。
这种副作用在界面上完全看不出来，只有下次打开列表才会发现顺序变了、归档没了。

表单里这几个字段用户改不了，但仍要参与校验与提交，并有测试专门盯着。

### 43. 表单校验必须和数据库唯一索引完全一致

分类的唯一索引是 `name`，活动的是 `(category_id, name)`。所以：

- 比较用 **trim 之后精确相等**，不做大小写归一 ——
  这里宽松、数据库严格，用户会遇到「界面说可以保存、底层却报错」；
  反过来则会放进重名数据；
- 活动的重名只比**同一分类**下的兄弟，别的分类有同名活动是允许的；
- 编辑时要把**自己排除**在重名比较之外，否则「名字都没改」保存按钮却是灰的。

三条各有独立测试。

### 44. 名称长度限制是主动加的护栏

需求没有规定长度，但分类名会出现在时间轴、日历格子、统计排行里。
一个三十个字的分类名会把界面撑坏，而用户不会因此得到任何好处。

所以主动设了 16 字上限，并**把上限写进错误提示**（「名称最多 16 个字，再短一点吧」），
让用户知道该怎么改，而不是甩一句「名称不合法」。

### 45. 表单校验结果不写成泛型

本来想用一个 `FormResult<T>` 覆盖分类与活动，但泛型密封类在调用处与测试里都要处理类型参数 ——
`as FormResult.Valid` 这种写法根本不成立（编译器要求类型参数），
写到最后反而比多写四行更难读。

最后是两个非泛型的 `CategoryFormResult` / `ActivityFormResult`，
与模块 9 的 `GoalFormResult` 形状一致：调用处与测试都不需要任何转型技巧。

### 46. 课表按「星期」组织，而不是按日期

用户想的是「周一有什么课」，不是「九月七号有什么课」—— 这也是课程表和普通日程列表最大的区别。
所以列表按周一到周日分组，**空的日子也列出来**：一周七格的骨架本身就在告诉用户「这里还能加课」。

单次日程（指定具体日期、不重复）单独一组：它没有「星期几」这个属性。
V1 的表单还不会创建这类条目，但界面也不能把它们藏起来 —— 那等于悄悄吞掉用户数据。

### 47. 时间用文本输入，不用时间选择器

课表里的时间是**挂钟模式**（「每周一 09:00」），用户打字五个字符就能填完；
而 Material3 的时间选择器在当前版本仍属实验性 API，引入它要承担版本风险。

更关键的是：解析逻辑放进纯函数之后，`9:00`、`09:00`、`9`、
`9：00`（中文输入法下很容易打出的全角冒号）这些**实际会被敲出来**的写法
全部能被测试覆盖，而不是靠肉眼在界面上试。
表单还会实时显示「时长：1 小时 40 分」，用户填完就知道对不对。

### 48. 跨夜合法，零时长非法

`结束 <= 开始` 表示跨过午夜（23:30–01:00 是需求五节支持的形态），
所以校验里**不禁止**它，并在界面上标出「跨夜」；
但 `结束 == 开始` 会被拒绝 —— 那等于把条目定义成 24 小时，几乎一定是误操作。

另外两条边界：开始不允许 `24:00`（领域模型要求 0..1439），结束不允许 `00:00`（要求 1..1440）。
这不是吹毛求疵：把它们交给领域模型去抛异常，用户看到的就是崩溃而不是提示。

### 49. 共用界面组件抽到 `ui/day`

`PickerOption`、`PickerList`（单选列表）与 `horizontalScrollable`（横向滚动修饰符）
原本分别写在目标管理与分类管理里。课程表表单也要用它们，于是统一搬到 `ui/day`
（放共用界面模型的地方）。

不抽就是三份几乎一样的实现 —— 正是「不要重复创建相似的数据类」要避免的；
抽出来之后，三处的行为（有没有颜色点、窄屏怎么滚）也自然保持一致。

### 50. 首页的计划分组始终显示

即使今天没有计划，首页也显示「计划 vs 实际」这一块，配一句提示与「课表」入口。
理由：「计划 vs 实际」是产品核心，但如果用户从没见过这一块，他就永远不会去录课表 ——
**功能存在但没人知道，等于不存在**。

### 51. 事后确认只问「说不清的部分」，而且要挑得准

需求三节 C 的原文是「只要求用户确认 15:30–16:00 做了什么，而不是让用户重新记录整个下午」。
所以这一页只列两类内容：

- **时间轴上真正占着位置的**推测记录 —— 一条推测如果整段都被用户手写的记录覆盖了，
  它在时间轴上根本不存在，再拿出来问只会让人莫名其妙；
- **十分钟以上**的缺失时间 —— 三分钟的空档问一次「你做了什么」，
  用户很快就会把这个 App 的通知关掉，而通知一关，整个闭环就断了。

`ConfirmationStateMapperTest` 把这些挑选用例逐条钉住（该问的、不该问的、门槛）。

### 52. 一键确认是主路径，想改才打开表单

待确认的每一条都先用系统推断的结果填好，用户觉得对就直接点「确认」（一次点击），
想改才点「修改」。要求用户每次都必须打开表单重选一遍分类，就违背了「低操作成本」。

多条时才出现「全部确认」—— 只有一条时逐个点反而更快，多一个按钮只是噪音。

### 53. 缺口只能「补记」，不能「忽略」

没有做「忽略这段时间」，也没有为此加表结构。理由：这个产品对「不知道去哪了的时间」
给出的答案是**一条记录**，而不是「不重要」—— 种子分类里本来就有「睡眠」「生活」，
用户完全可以说「这是在睡觉」。

加一个「忽略」按钮，等于给了用户一条把账做平的路，而这个 App 存在的意义恰恰是把账记清楚。
如果将来发现确实有用户长期不理会某一段固定时间，正确的做法是引导他录成一条真实记录，
而不是加个忽略把账做平。

### 54. 提醒的重点是「什么时候**不**提醒」

需求十二节要求「提醒必须低打扰，不能强迫用户完成记录」。
一个每天定时响三次的 App，用户三天内就会把通知关掉 ——
而通知一关，「事后确认」这条闭环就彻底断了。所以每个节点都有明确的**跳过条件**：

| 节点 | 提醒什么 | 什么时候跳过 |
|---|---|---|
| 中午 | 确认上午没记录的时间 | 上午不缺东西，也没有待确认记录 |
| 晚上 | 今天还有哪些目标没完成 | 目标都达标了，也没有待确认记录 |
| 凌晨 | 进入每日复盘 | 这一天完全没有任何数据 |

### 55. 凌晨 4 点那条必须静默

凌晨响铃会把人吵醒：既违背「低打扰」，也几乎必然导致卸载。
需求原文也说「4:00 的通知不是强制结算，而是进入每日复盘」——
它是「这一天整理好了」的告知，不是催办。

所以它是**静默通知**：不响铃、不弹横幅，只躺在通知栏里，用户醒来自然看得到。

### 56. 「上午」按准确的中午时刻切，不用「日边界 + 8 小时」硬算

中午那条只关心上午。缺口可能横跨中午（11:00–14:00），只把落在中午之前的那一段算进去。

实现上不硬算中午，而是让调用方用 `DayBoundary.millisAtMinuteOfDay(day, 12 * 60)` 给出准确时刻 ——
夏令时切换日两者会差一小时，而这种差异在一条通知的文案上完全看不出来，只会让人觉得「数字不对」。

### 57. 复盘提醒针对的是「刚刚结束的那一天」

它的触发时刻落在**次日 04:00**，但复盘对象是前一天。
所以 `ReminderTrigger` 同时带 `triggerMillis` 与 `targetEpochDay`：
只带触发时刻的话，复盘通知里会显示成明天的日期。

### 58. 提醒逻辑放在 `ui/reminder`，不放在 `domain`

它产出的就是通知文案（用户直接看到的文字），属于用户界面的一部分。
`domain` 层保持不含任何文案 —— 这条边界在模块 10 立过一次，这里继续守住。

**本轮只做逻辑层**：决定「要不要打扰、说什么」的规则全部是纯函数、已完整测试。
真正把通知发出去的平台层需要真机验证，放到下一个模块，
那部分代码会在 README 里明确标注**尚未经真机验证**。

### 59. 平台层只负责「准备数据、发出去」

`ReminderReceiver` 里几乎没有判断：拿到是哪个节点 → 取当天数据 → 交给 `ReminderPlanner` → 发送。
「该不该提醒、说什么」全在纯函数里（已测）。这样即使平台层某处写错了，
也不会让产品规则跟着错 —— 换个平台实现只需要重写那几十行。

### 60. 非精确闹钟 + RTC：提醒不是闹钟

- `setInexactRepeating` 而不是精确闹钟：提醒晚十几分钟毫无影响，
  换来的是省电，以及**不需要申请 `SCHEDULE_EXACT_ALARM`**
  （Android 12+ 上那需要用户去系统设置里单独授予，多数人不会去点）。
- `RTC` 而不是 `RTC_WAKEUP`：不唤醒熄屏中的设备，系统会在设备下次醒来时补发 ——
  这正好符合「低打扰」，凌晨那条尤其不该把手机叫醒。
- 同一节点用固定的 `requestCode`，所以重复调度是幂等的（替换而不是叠加）：
  启动时与开机后各调一次都不会造成重复提醒。

### 61. 两个通知渠道，不是一个

如果凌晨复盘和中午提醒共用一个渠道，用户要么全开要么全关 ——
那等于把「凌晨别吵我」这个诉求交给用户自己忍受。
分成两个渠道之后，用户可以在系统设置里单独关掉任意一个，而静默渠道本身没有声音与震动。

### 62. 开机后必须重新安排闹钟

系统闹钟在重启后会被清空。没有 `BootReceiver`，用户重启一次手机提醒就永久失效了，
而这种「功能悄悄消失」的问题用户很难自己定位。

它的 `exported` 必须是 `true`（`BOOT_COMPLETED` 是系统广播，未导出的接收器收不到），
因此它只做「重新安排闹钟」这一件事，不接受任何外部指令。

### 63. 这一轮到底验证到了什么程度

诚实交代，避免误判完成度：

- **已验证**：编译通过、571 个用例通过、**合并后的清单里接收器、权限、`<queries>` 都在**
  （这是在这台机器上能对平台层做的最实在的验证 —— 它证明接线真的进了 APK）；
- **未验证**：通知是否真的出现（需要 POST_NOTIFICATIONS 授权）、闹钟是否按时触发
  （非精确闹钟会被系统合并或推迟）、重启后是否恢复、厂商 ROM 的省电策略会不会杀掉它。

**装到手机上如果通知不响，最可能的原因就是通知权限没给。**

### 64. 记录编辑用「分钟数 + 日历日」，不用时间戳

用户看到的是 `14:00–15:30`，所以编辑也应该是这两个时刻。
但它们要落回绝对时间戳，必须知道**属于哪一天** —— 表单因此带上记录开始所在的**日历日**。

这里有个容易写错的地方：一条 02:00 开始的记录，它的**逻辑日**属于前一天，
但它的挂钟时刻 02:00 属于**当天的日历日**。用逻辑日去重建时间戳，会整整错一天。
`RecordEditFormTest` 里专门有一条用例盯着这个往返（02:00 的记录编辑后必须还在 02:00）。

### 65. 「结束 == 开始」是瞬时记录，不是跨夜

这是本次编辑功能里最要紧的一条判断。三种情况必须分开：

| 结束 vs 开始 | 含义 | 结果 |
|---|---|---|
| 结束 > 开始 | 普通记录 | 结束落在同一个日历日 |
| 结束 == 开始 | **零长度瞬时记录**（只记了次数） | 起止同一时刻 |
| 结束 < 开始 | 跨过午夜 | 结束落在下一个日历日 |

把「相等」也当成跨夜，一条「今天做了 2 题」的记录会变成 **24 小时** ——
界面上它只是一行 `24h`，不特意看根本发现不了。课表那边（模块 11）
反而把「相等」判为非法，因为一门 0 分钟的课没有意义；两处规则不同是有意的，
但都必须有测试盯着。

### 66. 编辑从仓库取记录，不从界面上那一行取

界面上的时间轴行是**裁剪过**的：跨 4:00 的记录在今天只显示属于今天的部分。
如果拿这一行当编辑起点，用户打开编辑框点保存，记录就被悄悄改短了。
所以 `startEditRecord` 走 `getRecord(id)` 取**完整**记录，编辑框里显示的也是完整起止。

同理，一条记录被更高优先级的记录从中间穿过时，时间轴上是**多行指向同一条记录**
（`TimelineRow.recordId` 因此不唯一）。编辑其中任意一行，改的都是整条记录 ——
这一点写在 `TimelineRow` 的注释里，并有测试断言「拆分后的两行 id 相同」。

### 67. 编辑一条系统记录 = 用户确认了它

保存走的是 `updateRecord`，仓库会把 `SYSTEM`/`SUGGESTED` 的来源改成 `MERGED`
（用户确认过的结果），而已经是 `MANUAL` 的记录保持 `MANUAL` 不降级。
这意味着「改一下时间」顺带完成了确认 —— 这是对的：用户既然动手改了，
说明他已经看过并且认可了这条记录的存在，只是细节不对。

### 68. 允许把一条记录的归属清空

编辑时可以取消分类与活动，记录变回「未归类」。
系统刚采集到的记录本来就是这个状态，所以它是合法状态，不该被拦住
（这是与「事后确认」的区别：那里问的是「这半小时你干了什么」，
一个都没选等于没回答问题，所以必须选一个）。

### 69. 记录编辑抽成共用的控制器，不写两遍

首页和日历都要「点时间轴的一行 → 改这条记录」。两边各写一遍的话，
差异会出现在最容易漏的地方（一处换分类时清空了活动、另一处没清），
而用户要等保存失败才会发现。

所以状态与动作放在 `ui/day/RecordEditController`：它不是 ViewModel，没有 Android 依赖，
只拿一个协程作用域；两个 ViewModel 各持有一个，把 `snapshot` 交给
`RecordEditorUiMapper` 合成界面状态。**界面要显示什么仍然是纯函数决定的**，
两个页面的编辑框长得完全一样，行为也完全一样。

### 70. 时间解析只有一份实现

`TimeOfDay`（`ui/format`）统一提供「一天中的第几分钟」的解析、格式化与时长文案，
课表与记录编辑共用。原先这三段代码长在 `PlanForm` 里，
本轮把它们搬了出来并把测试也一起搬走 ——
否则会留下「测试还在测旧入口」的假绿灯：两处实现各自被自己的测试覆盖着，
直到某天用户在其中一个表单里打不出全角冒号。

### 71. 事件常量来自 `android.jar`，不是凭记忆

`UsageEvents.Event` 的常量值在实现前用

```powershell
javap -constants -classpath <sdk>/platforms/android-36/android.jar 'android.app.usage.UsageEvents$Event'
```

直接从**编译这个 App 用的同一份 SDK** 里读了出来，然后把结果写进
`UsageEventTypes` 并配了断言测试。需求十六节第 11 条要求「先确认官方行为再实现」，
这就是那一步的证据 —— 而不是「我记得 MOVE_TO_FOREGROUND 是 1」。

顺带确认了两件容易写错的事：
1. `MOVE_TO_FOREGROUND`（旧名）与 `ACTIVITY_RESUMED`（新名）**值相同**，
   所以一个分支覆盖两个版本，不需要按 Android 版本写两套；
2. `FOREGROUND_SERVICE_START = 19` / `STOP = 20` 是前台**服务**，
   归入 `OTHER`，不参与会话重建（见第 72 条）。

### 72. 前台服务起停不算「用户在使用」

后台放音乐、常驻推送服务都会发 19 / 20。把它们当成「用户在用什么」，
一个晚上就会凭空多出几小时使用记录 —— 而且这种错误看起来完全像真的。
所以只有 `ACTIVITY_RESUMED` 才算会话开始。

### 73. 只跟踪「当前前台的那一个 App」

安卓同一时刻只有一个 App 在屏幕上，但事件流并不是整齐的：
切 App 时**新 App 的 RESUMED 常常先到、旧 App 的 PAUSED 后到**。
如果按包名各自开一个会话，就会得到两段重叠的会话 —— 那等于说用户同时在用两个 App。
所以这里维护唯一一个当前会话：谁到前台谁接上，上一个立刻结束。
结果天然互不重叠，正好满足 `TimelineResolver` 的输入假设。

同理，**不属于当前 App 的 PAUSED 一律忽略**：那是乱序到达的旧事件
（它的 RESUMED 甚至可能在窗口之前），照它结束会把正在用的 App 提前截断。

### 74. 短会话丢掉，不并进相邻会话

用户切出去看一眼消息再切回来，会留下 30 秒的碎片。丢掉它，而不是并进前一个 App ——
合并等于**捏造时间**：把用户没在用那个 App 的 30 秒算进它的时长里。
丢掉更诚实，而复盘里的「缺失时间」本来就能表达这几秒的空白。

阈值（默认 1 分钟）在**裁剪之后**判断：被 4:00 边界切剩 20 秒的会话同样不值得记一笔。

### 75. 未归类的记录照样写，并把 App 名放进备注

有一种做法是「映射没确定就不写记录」。那样用户会看到一段空白，
而在这款 App 里空白恰好意味着「没记录」—— 他只会以为系统坏了。
所以未归类的段也写成 `SUGGESTED`，分类留空，App 名进备注。

配套改了时间轴与确认页的标题兜底顺序：
**活动名 → 分类名 → 备注 → 「未归类」**。
一段还没归类的使用记录，唯一能说明它是什么的就是备注里的 App 名，
显示「微信」远比显示「未归类」有用 —— 用户看一眼就能说「对，那是社交」。
时间轴那一行同时限制为一行并省略，避免长文本把排版挤歪。

### 76. 用户归类过的 App 不再问第二遍

| 情况 | 来源 | 需要确认 |
|---|---|---|
| 用户确认过的映射 | `SYSTEM` | 不需要 |
| 有归属但没确认过 | `SUGGESTED` | 需要 |
| 映射没定归属 / 没见过这个包名 | `SUGGESTED` | 需要 |

**这张表就是「少记录」的落点**：用户归类过的 App 之后完全自动；
没归类过的问一次，确认后（`confirmMapping`）就永久自动了。
把一切都写成「待确认」，等于让用户每天确认二十次同样的事情 —— 那不是少记录，是换了个方式记账。

### 77. 置信度说的是「归属有多可信」，不是「时间有多准」

时间来自系统，是事实。置信度低是因为**不知道用户在干什么**（0.3 = 只知道用了这个 App）。
把它理解成对时间的怀疑，会让人以为记录本身不可靠 —— 那会毁掉用户对时间轴的信任。
所以确认页上写的是「系统推测 · 置信度 30%」，指的是归属。

### 78. 重新分析 = 先清空再写入，而不是靠幂等键增量写入

增量写入看似更省事，但有个致命问题：**改了 App 映射之后不会生效**。
幂等键命中时写入会被跳过，于是用户把「微信」归到社交之后，时间轴上那几段仍然是未归类 ——
他会以为这个功能坏了。重新分析这一天的语义正好就是「按现在的映射重算一遍」。

清空只碰 `SYSTEM` / `SUGGESTED`（写在 SQL 里，不靠调用方自觉），
手动记录与用户确认过的 `MERGED` 记录永远不在范围内 ——
所以**用户自己改过的结果不会被系统打回**。
另外幂等键仍然在被确认的记录上，所以重新分析也不会为同一段会话再写一条重复的。

为此给仓库加了一个 `clearSystemGeneratedIn(range)`：不能连着调两次
`replaceSystemGeneratedIn`（先 SYSTEM 后 SUGGESTED），因为第二次会把第一次刚写进去的清掉。

### 79. 分析窗口的结束时刻必须收在「现在」

用「日窗口 = 04:00 ~ 次日 04:00」直接当会话结束，此刻还在用的 App 会被记成
**一直用到凌晨四点**。所以 `analyzeDay` 把窗口结束取 `min(窗口结束, 现在)`，
并有测试断言这一条（`an app still in use is recorded up to now not to the end of the day`）。

同理，分析「今天」以外的日子（未来）直接返回空，不写任何东西。

### 80. 跨 4:00 的会话在两天各留自己那一段

会话按窗口裁剪，所以**系统记录永远不会横跨分界线**，「按开始时刻归属」这条规则
在系统记录上不会被绕过。幂等键里带上了**哪一天**，否则两天算出的键相同，
第二天的写入会被当成重复采集而跳过 —— 那半天就凭空消失了。

回看窗口默认 6 小时：只取当天窗口内的事件，会导致凌晨 03:50 打开的 App
在 04:00 之后那一段彻底消失（窗口里只有它的 PAUSED，没有 RESUMED）。

### 81. 删除系统记录后重新分析会复活它（已知取舍）

软删除的行仍然占着幂等键，而「重新分析」的语义就是清空+重建 ——
所以用户删掉一条系统记录，下一次分析会把它重新生成出来。
真正的「再也不要这条」需要一个忽略清单，V1 不做，但**必须写清楚**，
否则用户会以为删除失效了。可行的替代做法：把它归到一个分类（归类后即变成 `SYSTEM`，
不再被重新推断覆盖），或者直接编辑它 —— 确认过的记录（`MERGED`）不会被重新分析改动。

### 82. `PACKAGE_USAGE_STATS` 声明它不等于拿到它

这是一个容易搞错的地方，两件事必须分开：

1. **在清单里声明** `android.permission.PACKAGE_USAGE_STATS` —— 作用不是「获得权限」，
   而是让本 App **出现在系统设置的「使用情况访问」列表里**。
   不声明的话，用户在那张列表里根本找不到我们，也就永远授权不了。
2. **判定是否真的给了** —— 不能用 `checkSelfPermission`（它不是运行时权限），
   要查 AppOps：`OPSTR_GET_USAGE_STATS` 只有 `MODE_ALLOWED` 才算给了，
   **`MODE_DEFAULT` 表示「还没问过用户」，等于没给**。

版本差异也按第 71 条的做法先确认再用：API 29 起 `unsafeCheckOpNoThrow` 才是安全的查法，
旧版本只有 `checkOpNoThrow`；两个方法都存在于本机 `android.jar` 里，所以按版本选一个调，
而不是赌某个方法在所有版本上都不抛。个别 ROM 连这个查询本身都会抛 `SecurityException`，
此时按「没给」处理 —— 引导用户去设置页看一眼，比在这里崩掉有用。

### 83. 采集区间固定重读，不用「上次采集到哪」的游标

数据层有 `getLatestEventMillis()` 游标，但这里刻意不用：事件可能因为权限被撤销、
系统清理历史、或用户在别的时区飞行而出现空洞，**靠游标增量推进一旦错过一次就永久错过**。
重读的开销很小（一次查询两天多的数据），而落库靠 `event_key` 幂等去重 ——
重复读不会写重复数据，代价只是几毫秒。测试里专门断言了「读两次，第二次新增 0 条」。

### 84. 连「昨天」一起分析

逻辑日是 04:00~次日 04:00。凌晨 2:00 的使用属于**昨天**，
只分析今天的话那一段永远不会被生成出来 —— 用户翻到昨天会看到一天空白，
而这恰好是「熬夜学习」最需要被看见的时段。

### 85. `getNextEvent` 复用同一个对象，必须立刻取值

`UsageEvents.getNextEvent(event)` 是把下一条事件**填进你传进去的那个对象**，
不是返回新对象。每次循环都要立刻把字段拷出来，否则整个列表会是同一个对象、
内容全是最后一条 —— 编译通过、运行不崩，只是时间轴莫名其妙全变成同一个 App。
这条坑写在 `AndroidUsageEventReader` 的类注释里，因为它是最难靠测试发现的一类错误
（平台层测不了，只能靠注释和真机）。

### 86. 包可见性只要 LAUNCHER 应用，不要 `QUERY_ALL_PACKAGES`

Android 11 起查询别的 App 需要声明可见性。为了让时间轴显示「微信」而不是
`com.tencent.mm`，只需要 `<queries>` 里声明「带 LAUNCHER 入口的应用」——
这是官方推荐的、比 `QUERY_ALL_PACKAGES` 克制得多的做法：
我们只需要给用户看得见的 App 起名字，不需要枚举整个系统。
解析失败（已卸载、系统组件）一律回退显示包名，**不会因此少一条记录**。

### 87. 采集时机是「回到首页」，不引入后台任务

没有用 `WorkManager`，也没有常驻服务：这款 App 的数据只有在用户回来看的时候才需要新，
额外的后台任务只会带来「为什么它在后台跑」的疑问和耗电。
所以时机就是**每次回到首页时读一次**，它同时覆盖了三种情况：刚授权、权限被撤销、隔夜回来。

配套的 `OnResumeEffect` 也是自己写的（`LocalLifecycleOwner` + `LifecycleEventObserver`），
而不是用 `LifecycleEventEffect`：后者是较新版本才有的入口，这里没必要为它承担版本风险。

### 88. 「没授权」和「已授权但系统里还没记录」必须分开说

这是这一块界面存在的唯一理由。两种情况都写成「暂无数据」的话，
用户会一直去点授权按钮 —— 而问题根本不在于权限。

所以文案分成三态：未授权（一个按钮 + 说明「只读使用时长，不会读取任何内容」）、
读取中、已授权但系统里还没有可用记录（明确说「刚授权或今天还没怎么用手机时都是这样」）。
已授权时还留一个「重新读取」按钮：有些 ROM 的数据会延迟写入。

统计口径也一并说清楚：「读出 5 段时间，3 段已自动归类，1 段待确认，
2 段与你的记录重叠（以你的记录为准）」—— 最后那句是必须的，
否则用户会以为自己记的东西被系统吃掉了。

### 89. 「待归类」不等于「归属为空」

界面分成「待归类」和「已处理」两组。分组规则不能简单写成 `categoryId == null && activityId == null`，
因为用户可能已经明确说过「这个 App 不用归类」—— 那时归属仍然为空，但 `isUserConfirmed` 为 true。

把它算成待归类的话，用户刚做完决定，那个 App 还赖在待办列表里，他会以为没保存成功。
所以规则是 **`未确定归属 且 用户没表过态`** 才算待归类，其余一律进「已处理」。

### 90. 系统猜的归属必须标出来

有归属但用户没确认过的（内置默认映射），标签后面加「（系统推测）」。
不标的话，用户会以为「娱乐」这个归类是自己定的 —— 而实际上那条记录还躺在待确认列表里等他点头。
这类「界面看起来已经定了、实际还没定」的错觉，比直接显示「未确定」更糟。

### 91. 按最近使用排序，且只算前台事件

用户的时间和注意力有限，先处理「昨天刚用了两小时」的那个 App，比按包名字母序有意义得多。
「最近用过」与「打开 N 次」都只统计 `ACTIVITY_RESUMED`：
熄屏、锁屏也发事件（而且没有包名），混进来「打开 12 次」这句话就不成立了。

### 92. 「什么都不选就保存」是合法输入

它表示**这个 App 不用归类** —— 仓库会把 `isUserConfirmed` 置为 true，
之后推断层直接写 `SYSTEM`，不再拿它来问用户（`UsageRecordInferrerTest` 里有断言盯着这个衔接）。

对话框里必须写清这一句：不然用户会以为自己没填完，
而这个功能的全部意义就是「说一次，之后别再问」。

### 93. 归类页的入口放在状态块上，不占第四个 Tab

它是一个**把系统数据整理干净的一次性动作**，不是每天要看的东西。
所以入口是首页系统感知状态块上的「去归类」（只有确实有未归类 App 时才出现），
页面本身走二级页面的返回栈。

状态块里已经写着「N 个 App 还没归类」—— 只说问题不给入口的话，
用户得自己猜这个功能藏在哪儿，而它恰恰是「少确认」的开关。

### 94. 这一轮踩到的两个坑（都靠测试发现）

1. **测试断言错了分组。** 我第一版测试认为「系统猜了归属的 App 应该出现在待归类里」，
   而设计上它属于已处理（记录会在待确认列表里被确认，那是另一条路径）。
   查下来是**测试写错了**，不是代码错了 —— 顺手补上了第 90 条的标记，把两者的区别显式化。
2. **文案里的多余空格。** `"最近 $relative 用过"` 拼出「最近 2 小时前 用过」。
   中文里数字与汉字之间的空格是有意的排版，汉字之间的不是。
   改成 `"${relative}用过"` 之后，两种相对时间（「刚刚用过」「3 天前用过」）都读得通。

### 95. 清理原始事件必须和分析范围解耦

`usage_events` 是唯一会持续增长的表（一天几百条）。它有保留策略（60 天），
但**清理本身是危险的**，因为它和「重新分析」的语义撞在一起：

重新分析某一天的第一步是「清空这一天的系统记录再重建」。如果那一天的原始事件已经被清掉了，
结果就是**清空了、却什么都重建不出来** —— 那一天的记录会凭空消失，而且没有任何报错。

所以保留策略必须配一条守卫：`UsageAnalysisService` 只分析最近 30 天，
更旧的日子**直接跳过（不清空、不重建）**。清理窗口（60 天）比可分析窗口（30 天）宽一倍，
边界上不做危险的事；而实际只会分析今天与昨天，所以正常使用中根本碰不到这条边界。

清理的**顺序**也不能反：先分析、后清理。反过来会把当天要用的数据清掉。

### 96. 把「无法验证」变成一张能勾选的清单

到模块 19 为止，README 里散着十几处「⏳ 需真机」。它们诚实，但**不可执行** ——
拿到手机的人不知道该按什么顺序试、看到什么算正常。

所以补了两份文档：

- [`docs/GETTING_STARTED.md`](docs/GETTING_STARTED.md)：五分钟走一遍的路径
  （授权 → 归类 → 建目标 → 看一天），以及需求十七节那三个验证问题**具体怎么试**。
  里面写的是「怎么试」，不是「结论」——后两个问题没有真机与几天数据是答不了的。
- [`docs/DEVICE_CHECKLIST.md`](docs/DEVICE_CHECKLIST.md)：逐条可勾选，
  每条都写了预期结果，标 ⭐ 的是「不通就等于这个模块没做成」。

这不是走形式：写完清单之后回头看，才发现有几条**从来没被任何人验证过**，
而它们恰恰是产品能不能成立的关键 ——
比如「归类一个 App 之后，它的记录是否真的不再需要确认」。

### 97. 判断标准不该是黑名单，而是「用户能不能点开它」

第一版只排除了三类（桌面 / 系统界面 / 输入法），结果归类页里躺着 **47 个待归类**，
混着权限管理、权限控制器、软件包安装程序、阅图锁屏、系统桌面（17 分钟）。
用户的反应很直接：**「我凭什么要给权限管理归类？」**

黑名单永远补不完（各家 ROM 包名不同）。所以改成问一句话：
**「这个东西，用户能自己在桌面上点开吗？」** —— 用 `getLaunchIntentForPackage` 判断有没有
`MAIN`/`LAUNCHER` 入口。在真机上逐条验证过：安装器 / 权限控制器 / 权限管理 / 系统界面 /
阅图锁屏 / 小V建议 / 健康使用设备 / **系统桌面** 全都没有桌面入口；
而设置 / 相机 / 相册 / 闹钟 / **vivo健康** / 计算器 / 浏览器都有 —— 后面这些用户确实会主动打开，该记就得记。

### 98. 「未归类就逐条确认」这条规则必须改（需求三节的字面理解是错的）

需求三节说「系统推测的记录要用户确认」。真跑起来它变成了 **47 条待确认**，
其中 77% 短于 5 分钟 —— 用户还没归类过任何 App，于是**每一条记录都在问他一次**。
那不是「少记录」，那是换了个方式记账。

改法不是「不问了」，而是**换个地方问**：
- 记录层不按条问 —— 「你用了微信 40 分钟」是可观测的事实，直接落库（`SYSTEM`）；
- 归类页按 **App** 问一次 —— 用户点一次「微信 = 社交」，之后永久自动。

所以 `SUGGESTED` 现在只留给「系统猜了归属但用户没点头」这一种情况。
这不是把需求做小了，是把「确认」放在它真正有意义的那一层。

### 99. 打扰用户是要算成本的

归类页现在只把 **用时 ≥ 10 分钟**的 App 列为「待归类」，其余收进
「另有 N 个用时很少的 App，不催你处理」。依据：47 个待归类里 24 个用时不到 1 分钟
（天气 0 分钟、信息 0.1 分钟、钱包 0 分钟）。

它们**照样被记录**在时间轴上（未归类），只是不催 —— 不催不等于藏起来：
那一行写着数量与合计时长，点开就能看到全部。

### 100. 时间轴需要一层折叠，但记录不能丢

> ⚠️ **这条已被决策 103/104 取代**：折叠会把「零碎使用」藏起来，而用户要的是
> 「一条竖轴、块高即时长」。现在是**显示分组**（合并成块但标注真实时长），不再折叠隐藏。

改造之后某一天生成了 **87 条**系统记录，其中 70 条短于 5 分钟。
这不是检测错误：间隔 1–5 分钟的地方确实没有任何 App 在前台（用户在看桌面、或手机搁着），
**碎片是用户真实的行为**。但 87 行罗列出来，人看不出「这一天是怎么过的」——
而那正是这款 App 要回答的问题。

所以时间轴分两层：**≥ 5 分钟单独一行，< 5 分钟折叠成一行汇总**（可展开、可编辑）。
两条例外必须记住：
- **用户自己记的或确认过的（MANUAL / MERGED）永远单独显示** ——
  把它折叠进「零碎使用」等于告诉他「你记的东西不重要」；
- **瞬时记录（只记了次数）也永远单独显示** —— 它没有时长，但确实是用户主动记的一笔。

折叠不等于隐藏：当天的总时长统计一直包含它们。

### 101. 诊断工具会随版本过期，验收要看 App 实际写出的东西

`diagnose_usage.py` 里有一份「按 App 规则重建前台会话」的实现，它跟着 App 的规则一起演进，
很快就落后了 —— 模块 20 加了排除系统组件、合并快速切回两条规则之后，它报出的
「被丢掉的碎片 2674 段」和改之前**一模一样**，差点让我以为改动没生效。

所以另写了 `tools/compare_records.py`：**只读 App 实际写进库里的记录**做前后对比。
教训是：验收要盯着产物，不要盯着一份自己维护的模拟实现 ——
模拟实现会跟着规则一起漂移，而产物不会。

### 102. 合并窗口决定「时长」，所以它必须紧；可读性交给显示层

用户看完时间轴之后的反馈是：「有些间隔一分钟然后是同一个应用的，可以直接并一起，
就设定五分钟左右」。照做之后装到真机上，**数据立刻失控**：

| | 数值 |
|---|---|
| 09-12 真实前台时间（原始事件逐段相加） | **5h18m** |
| 放宽到 5 分钟之后，写进记录的时长 | **9h58m** ✗ |

多出来的 4h40m 全是被合并掉的**空档**——一天有几百个「离开一下」，每个都 ≤5 分钟，
全都算进了 App 时长。第一次我以为只是「链式吞并」（抖音→微信→抖音 不断接回去），
修掉之后仍然虚报，才想明白根因在「合并本身会把空档算成使用时间」。

所以定了两条：
1. **数据层保持 30 秒**（只吃掉秒级误触），时长必须是真的 —— 时间记账的时长失真，
   整个产品就没有意义了；
2. **「太碎」是显示问题，在显示层解决**：同一个 App 在 5 分钟内重新出现就并成一块显示，
   块高按跨度画（轴才准），标注写**各段真实时长之和**（`24m（2 段）`）。
   数据一行都没动，统计因此不会虚报。

### 103. 时间轴是**竖轴**，不是列表也不是横带

我先后做过两版都不对：等高罗列的列表（用户：「用户想看的不会是单纯的罗列使用时间段」）、
横向彩色日带（用户：「nono，我设想的时间轴是一条竖立的轴，从上到下」）。

最终形态：从上（04:00）到下（次日 04:00），**块高 = 那段时间的长度**，
左边一列是每块自己的开始时刻（这就是刻度），一条细竖线贯穿全高，
空白段时间真的空着并标注 `空 2h10m`。用户的原话是
「将应用与时间轴一同打包，能够直观呈现」——高度比例就是他说的「直观」。

### 104. 显示分组只按 App，手动记录永不分组

分组键是**包名**（从记录的幂等键反解）。手动记录用记录 id 当键，也就是**永不分组**。

一开始按「分类 + 活动」给手动记录分组，测试立刻炸了：两条不同的手记被并成一块。
用户亲手写的两笔，哪怕归到同一个活动，也是两件事。

同理，**不同 App 永不合并**（抖音 + 王者 → 「娱乐」会丢掉「具体在用什么」，
而用户明确说他要看的就是这个）。

### 105. 空白按真实时长占位置，刻意不封顶

早先的版本给空白段设了高度上限（48dp），怕长空白把页面撑爆。做竖轴时去掉了：
**空白占多大地方，本身就是信息**——「上午三小时没碰手机」就该占三小时的位置，
这正是用户要的「留白」。一天的空档加起来也就几百 dp，页面长一点没关系。

矮块另有一条**下限**，而且它是「能不能点得到」的下限，不是「好不好看」的下限：
用户第一次看到竖轴之后的反馈是「你这个轴太挤了吧，想要修改时间都不太好操作，
我的建议是放大」。于是拿他的真实数据算了一遍（09-12：60 个记录块 + 10 个空白块）：

| 比例尺 | 09-12 总高 | 约几屏 | 最小的块 |
|---|---|---|---|
| 20dp/小时 + 下限 18dp（原） | 1313dp | 1.6 屏 | 18dp ✗ 点不准 |
| **30dp/小时 + 下限 36dp（现在）** | ~2500dp | **3.1 屏** | **36dp** ✓ |
| 40dp/小时 + 下限 44dp | 3106dp | 3.9 屏 | 44dp |

块是**整行宽**的，所以 36dp 高已经很好点；18dp 时用户明确反馈点不准。
所以轴是「分段线性」的——这一点写在映射器的注释里，免得后人以为算错了。

### 106. 熄屏分类（用户提的方案，已实现）

用户自己提出的：「或许可以设定一个熄屏的分类，这样就可以避免某个统计时间够长的风险」。
这个判断很准——它一次解决两件事：

1. **堵住合并的洞**：熄屏一旦是一条记录，它就成了「两段之间的东西」，
   合并规则可以明确地不跨过它；
2. **一天的账变成平的**：空白是「没有记录」（未知），熄屏是「手机没在用」（已知），
   对记账产品来说这两者意义完全不同。

用户定的口径：**熄屏完全参与统计**（不做单列），理由是「使用方可以后期修改熄屏时期
具体在做什么」。现有功能已经支持（点时间轴任意一行就能改分类），所以这条能成立。

实现的规则：熄屏 ≥1 分钟写成一条记录、<1 分钟仍可被合并吸收、**合并绝不跨越熄屏**。
「阈值必须大于合并窗口」是一条写死在 `UsageAnalysisService.init` 里的不变式 ——
否则同一段时间既被并进会话、又写成熄屏，会被算两次。

### 107. 重新分析按「起始时刻」清，不按「重叠」清

`clearSystemGeneratedIn` 最初的 SQL 用「时间段重叠」判定哪些系统记录要清。
系统记录都被裁剪到当天窗口，两者本该等价 —— 直到真机上出现：
夜里一段熄屏 `00:43 → 04:00` 被日志边界切成两天两段，属于前一天的那段**结束时刻正好等于
次日窗口的起点**，于是「重叠」判据命中，分析次日时把前一天夜里那段熄屏删掉了。
界面上表现为「夜里那段熄屏，每分析一次次日就消失一次」。

改法：判据换成 `start_time_millis >= rangeStart AND < rangeEnd`（起点在区间内），
与全局「按开始时刻归属」的规则完全一致。`TimeRecordRepositoryImplTest` 补了一条
回归测试锁死这个边界（前一天那段必须活着、当天那段正常清掉）。

### 108. 熄屏门槛从 5 分钟降到 1 分钟（先量，再改）

用户看完竖轴问：「间隔中的时间也没有进行分类，而是直接断开？那不进行分类（熄屏）？」
——他说得对，但**改哪个常数**不能凭感觉。上一次「看起来更整齐」的改动
（会话合并窗口 30 秒 → 5 分钟）把一天从真实 5h18m 变成了 9h58m，教训还在。

所以先写 `tools/threshold_probe.py` 在真机数据上把每个候选门槛都算出来，再决定：

| 熄屏门槛 | 一天几段 | 合计 | 备注 |
|---|---|---|---|
| ≥5 分钟（原） | 22 | 6h55m | 被亮屏打断的整段消失，正是用户看到的「直接断开」 |
| ≥2 分钟 | 46 | 8h01m | |
| **≥1 分钟（现在）** | **109** | **9h31m** | 扣掉被手动记录盖住的部分后，实际写入 6h14m |
| ≥30 秒 | 169 | 10h14m | 收益已很小，碎片却翻倍 |

选 1 分钟的理由是**人的行为**：拿起手机看一眼通常不到 1 分钟，
而把手机放下一般会超过它。30 秒只多拿回 43 分钟，却多出 60 段记录。

代价是记录条数（22 → 109），交给**显示合并**解决：相邻熄屏段的显示窗口放到 15 分钟，
块上写 `N 段` + 各段真实时长之和 —— 数据层诚实，轴上仍然是一块。
这和决策 102 是同一个分工：**门槛决定数据，窗口决定可读性**。

同一张表还量出了「空」的其余部分（这一轮没动）：
「真的在划手机但每次不到 1 分钟」占 4h51m（会话门槛 60 秒丢掉的），
「系统一条事件都没有」占 6h03m（关机 / ROM 历史，问谁都没用）。
前者要不要也记下来（门槛降到 10 秒：+1h00m 真实前台，记录 47 → 203 条）留给用户决定。

### 109. 复盘的一天只到「此刻」

`DayReviewService` 以前把整个逻辑日窗口交给聚合器，于是下午三点打开 App 会看到
「今天未记录 12h53m」—— 后面那 13 小时**还没发生**。饼图的分母（一天的账）也跟着错。

改法：观察窗口 = `[04:00, max(此刻, 当天最后一条记录的结束))`，再夹到逻辑日里。
带上「最后一条记录的结束」，是因为用户可以提前把**未来**的一段时间记上
（「今晚 20:00–22:00 自习」）；那种记录必须进统计，否则它会出现时间轴上却不进任何数字 ——
那是最难向用户解释的一类不一致。

窗口来自 `durations.window`（`DurationBreakdown` 自己带着它），
所以「有记录 + 没记录 = 已经过去」在**一个地方**成立，不会两处各算一遍。

### 110. 空白块要自己说明原因，不能只是一个空洞

用户的原话：「有些空的没有分类是怎么回事」。空白把三类完全不同的东西混成了一种：
手机真的没在用、用户在零碎地划手机、系统压根没有这段数据。

`UnrecordedGapClassifier` 把原始事件按空白段分桶，算出几个事实
（有没有事件、打开 App 几次、黑屏多久、**多少时间系统完全没有事件**），
措辞留给 `DayViewStateMapper` —— 界面文案仍然全部落在可测的纯函数里。

一条踩到的坑写在 `gapHint` 的注释里：第一版是「有事件就报事件」，
结果真机上最典型的那块空白（凌晨 04:00–07:43，前 3h40m 一条事件都没有、
最后 3 分钟有几条）被写成「零碎操作 6 次」——
数字没错，却把三个多小时的「没有数据」藏掉了。现在按谁占得更多决定先说哪一件，最多说两件。

### 111. 会话门槛 60 秒 → 10 秒（用户选的，仍然先量）

熄屏那一半解决之后，用户接着问的还是同一件事：那些「零碎的时间」为什么不分类。
这一次的答案不是「门槛太高」四个字，而是 **4h51m** —— 09-12 有四个多小时的跨度里，
用户确实在划手机，只是每次开 App 都不到 60 秒，被会话门槛整段丢掉了。

把四档门槛都算出来给用户看（`tools/threshold_probe.py`），他选了 10 秒：

| 门槛 | 一天几段 | 前台时长 |
|---|---|---|
| 60 秒（原） | 47 | 4h00m |
| 30 秒 | 83 | 4h26m |
| 20 秒 | 123 | 4h42m |
| **10 秒（现在）** | **203** | **5h00m** |

**为什么不更低**：10 秒以下基本是通知把 App 拉起来闪一下、以及 ROM 重复上报造成的假会话。

**一个必须一起改的地方**：`minSessionMillis` 同时是规则二里「中间那段算不算别人真的在用」
的判据。留在 60 秒的话，一段 30 秒的微信访问会被**吞进抖音的时长**里 ——
那正是「捏造时间」。所以两个角色必须共用一个值：**能成为记录的插曲就不许被吞掉**。
旧测试 `a quick switch away and back becomes one session` 用的正是 30 秒插曲，
它现在换成了 3 秒（仍然合并），并新增一条「30 秒插曲必须各自成块」。

### 112. 轴上画的是「一段连续在动的时间」，不是一条记录

门槛降到 10 秒的代价立刻出现：09-12 有 **369 条记录**。
一条一块地画，轴高 = 369 × 36dp 下限 ≈ 一万 dp（十几屏），而每块又矮到点不准 ——
用户之前抱怨的「太挤」会变成「太长」。

所以显示层再做一次聚合（`chunkForDisplay`，仍然是纯函数、可测）：

1. 间隔超过 15 分钟 → 真的空档，块在这里断开（那段留白照画）；
2. **用户自己写的记录永远单独一块** —— 他亲手记的每一笔都要能直接点到；
3. 同一个 App / 熄屏再次出现 → 直接接着收（原来的显示分组）；
4. 否则继续收，直到这一块里**记下来的时间**攒够 15 分钟。

块对外呈现的是**占得最多的那一个**（标题、图标、颜色都用它），标 `N 段`，
时长写整块里记下来的真实总和。**点一下展开**成每一条，每一条各自可点可编辑 ——
展开状态是界面的事（`rememberSaveable`），高度怎么算仍然在映射器里。

真机数据：09-12 的 369 条记录 → **47 块 + 2 块空白 ≈ 2~3 屏**；
09-13 的 113 条 → 28 块。信息一条没丢，只是默认折叠起来。

这和决策 102、108 是同一条纪律的第三次应用：**门槛决定数据，聚合决定可读性，
而两者都不许动「时长」这个数字**。

### 113. 应用饼图不能沿用分类色

用户要「具体应用的饼图」，第一反应是复用分类色（界面里所有颜色都来自分类，
这是从模块 8 起就定下的原则）。但真机数据立刻否掉了这个做法：
抖音、B 站、小红书、王者荣耀都归在「娱乐」下，用分类色画出来是一整块同色 ——
**用户问的恰恰是「娱乐里到底是谁」，而这张图回答不了**。

所以应用用一套固定色板、按排名取色（第一名永远同一个颜色）：
同一份数据每次画出来一样，不会刷新一次颜色全变。分类色仍然用在分类图上，
两张图的分工是清楚的：**分类看归属，应用看具体**。

同一条思路下的第二个自查：**「自己记的」那一片是补上的**。
手记没有包名，第一版在按应用分组时被直接跳过 —— 结果是圆环缺了 13% 的口子，
看起来像画错了。现在它单独占一片（睡眠、复习这些时间本来就该在图上），
并有一条测试钉住「各片加起来正好是已经过去的时间」。

### 114. 手机内置的使用统计是怎么算的（以及我们为什么对不上）

用户拿手机自带的「健康使用设备 → 使用统计」一比：「这跟手机内置的统计应用的时间并不一致，
能否看看那边是怎么统计的，一切最好以手机端内置的为主」。

先把内置那套读出来（截图 + `dumpsys usagestats` + `tools/aosp_model.py` 逐步验证）：

**内置读的是 Android 自己的聚合统计**（`UsageStatsManager.queryUsageStats`），
每个应用时长 = **该应用只要有任何一个 Activity 处于 resumed，时间就算给它**
（`UsageStatsService` 维护的是「当前 resumed 的 Activity 集合」，不是「当前前台的那一个 App」）。

把这条规则在我们自己的原始事件上实现一遍，就能和手机屏幕上显示的数字对上：

| 应用（09-13 截至 16:11） | 手机内置 | Android 口径重建 | 我们现在的记录 |
|---|---|---|---|
| 抖音极速版 | 1h54m | **1h54m** ✓ | 41m |
| 时间记账 | 1h37m | 1h27m | 1h31m |
| 王者荣耀 | 38m | **38m** ✓ | 1m |
| 哔哩哔哩 | 28m | 18m | 28m |
| 全天合计 | 6h50m | 6h39m | 3h55m |

**我们差在哪 —— 两个机制，都能从数据里指出来：**

1. **同一个 App 内部换 Activity，被我们当成了「切走」**。抖音的原始事件是这样的：
   `00:13:59 PAUSED / 00:13:59 RESUMED / 00:14:00 STOPPED`，一秒内成对出现几十次。
   Android 口径下这个 App 一直在前台（它的另一个 Activity 接上了）；
   我们的模型是「谁最后 RESUMED 谁在前台，别人一 PAUSED 就结束这一段」，
   于是一段 1h54m 被切成几十段，短于 10 秒的还被丢掉 —— 只剩 41m。
2. **别的 App 冒出后台 RESUMED，把真正在用的那段切断**。12:17 打王者那一段
   （原始事件 12:17:03 → 12:40:07，38 分钟）期间 QQ/微信/桌面不断冒出 RESUMED，
   我们的单会话模型一看到别人 RESUMED 就把王者结束掉 —— **那 23 分钟整段没有记录**。

顺带发现第三个副作用：**被编辑过的记录占着幂等键**，重新分析会跳过它，
所以「被编辑错的值」会一直留着，哪怕原始事件后来变了。

**下一步（模块 26，两件事分开做、各自验证）：**

1. **会话重建改用 Android 的归属口径**（按「(包名, Activity) 的 resumed 集合」记账，
   时间算给所有还有 Activity 在前台的 App）。这是两边数字对不上的**主因**。
   会话之间会出现重叠，而时间轴要求不重叠，所以还要定一条归属规则（谁最后到前台谁占）。
2. **日界线 4:00 → 0:00**（用户的选择：与手机完全对齐）。这一改会动到 35 条
   写死 4 点语义的测试，所以单独一轮做，不和上面那件混在一起 ——
   否则出了偏差分不清是谁造成的。

三条**改完仍会存在**的差异，先说在前面：日界线（0 点对齐后消失）、
重叠时段（Android 两边都算，我们只能给一个）、系统界面（内置合计含桌面，
今天 26 分钟；我们按模块 20 的约定不算「用户在用什么」）。

### 115. 会话模型改成 Android 的归属口径（模块 26 第一件）

按决策 114 的结论重写了 `ForegroundSessionBuilder`，四处改动都有真机依据：

| 改动 | 依据 |
|---|---|
| 按 **(包名, Activity)** 记账，一个包只要有 Activity 在前台就一直算 | 抖音换 Activity 的抖动（一秒几十次 PAUSED/RESUMED）；旧模型把 1h54m 切成几十段 |
| **熄屏 / 锁屏不再替应用收尾**，交给应用自己的 PAUSED | 这台 ROM 在视频播放、屏幕闪烁时也发熄屏事件（32 分钟里 136 次），而应用的 PAUSED 并不到 |
| **合并要在筛选之前**（先合并、再按门槛筛） | 顺序弄反过一次：先筛就把抖动的 0.x 秒小段全丢了，永远合不回来 |
| 重叠段落按「**最后到前台的那个占这一段**」切 | Android 允许两个 App 同时算，而时间轴要求一段只属于一个 |

改完当场量到：王者荣耀 1m → **24m**（真机 38m）、时间记账 1h31m ≈ 内置 1h37m ✓。

**还差的 40 分钟，原因查清了：是用户自己早先编辑过的记录挡住的。**

过程值得记下来，因为中间有三个假设被实测否掉：
1. ~~「手动记录保护」整条拒绝~~ → 实现了「绕着手动记录切段写入」（`clipAroundManual`，
   这个改法本身是对的，留着了），但改完抖音仍然 34m；
2. ~~「熄屏替应用收尾」~~ → 去掉之后 36m 只变 35m；
3. ~~「多窗口/切换瞬间两个 App 同时算前台」~~ → 实测重叠只有 **5 分钟**。

真正的定位办法是**把构建器的四步逐步打出来**（`build/diagnose/trace_builder.py`），
于是看到原始段只有 31m、而 AOSP 口径是 1h35m —— 差额在**第一步**。
第一步里唯一与 Android 不同的东西是我自己加的一条「兜底」：
*PAUSED 的类名对不上时，就关掉这个包里最早开着的那个 Activity*。
这台 ROM 报的类名前后并不一致，于是每个对不上的 PAUSED 都把正在用的 Activity 关掉一次。
**删掉兜底之后，原始段 31m → 1h35m**，与 Android 口径一致（王者也随之上到 36m，
手机内置 38m）。

剩下的差额是另一回事：抖音在 09:18、10:30、11:14 那几段被**用户编辑过的记录**
（MERGED）占着同一个幂等键 —— 重新分析按规矩跳过它们，于是用户当初在**错的会话边界**上
编辑出来的短时长一直留着（12m 而不是 40m、8m 而不是 20m）。
这不是 bug，是「保护用户编辑」与「跟随新算法」之间的冲突，需要用户拍板：
是保留他的编辑，还是**保留他改的归类、把时间按新算法延长**。

`diagnose_usage.py` 里有一份「按 App 规则重建前台会话」的实现。模块 20 给 App 加了
排除系统组件、合并快速切回两条规则之后，那份实现就落后了 —— 它报出的
「被丢掉的碎片 2674 段」和改造前**一模一样**，差点让我以为改动没生效。

所以另写了 `tools/compare_records.py`：**只读 App 实际写进库里的记录**做前后对比。
教训是：验收要盯着产物，不要盯着一份自己维护的模拟实现 ——
模拟实现会跟着规则一起漂移，而产物不会。

### 已知局限（重要）

`FakeDaos.kt` 把 SQL 里的判定条件（区间重叠、幂等键唯一、软删除过滤）在 Kotlin 里重写了一份，
因此它验证的是**仓库的编排逻辑**，而不是 Room 真的会那样执行 SQL。

同样的道理适用于 `FakeUsageRepositories.kt`：`ensureDefaultMapping` 的语义
（用户确认过的映射只允许刷新展示名、归属与置信度一个字都不动）在替身里也重写了一份。
**替身比真实现宽松的话，测试就会给出一条假绿灯** —— 写这一轮时恰好踩到：
第一版替身是「已存在就直接返回」，于是「采集不会覆盖用户确认的映射」这条断言
测的其实是替身自己的行为。发现后把替身对齐了真实现，断言也改成真正该守的东西
（归属与置信度不变，而不是整个对象不变）。

SQL 本身（索引、唯一约束、`UPDATE ... WHERE source IN (...)`）需要连真实 SQLite 才能验证，
属于 Robolectric 或仪器化测试的范围，**本轮没有引入**。
引入 Robolectric 需要它能从镜像下载 `android-all-instrumented` 运行时包，
这一点尚未验证 —— 如果要补，先确认镜像可用再动手。

**UsageStats 平台层**（`AndroidUsageEventReader` / `UsageAccess` / `AndroidAppLabelResolver`）
是唯一无法在本机验证的一层：它只做「取数、判权限、查应用名」三件事，
所有判断逻辑都在 domain 层并被测试覆盖。

3. 走查与试用之后，再决定 V2 做什么：
   目前已知的候选是「忽略某条系统记录」（决策 81 的取舍）、
   单次日程的界面（数据层已支持）、以及按使用场景调整推断规则。

### 已经做完、但只能在真机上确认的部分

- 全部界面的**观感**（首页 / 日历 / 统计 / 目标 / 分类活动 / 课表 / 事后确认 /
  记录编辑 / 系统感知状态块 / App 归类页）；
- 提醒是否真的弹出、闹钟是否按时触发、重启后是否恢复；
- **「使用情况访问」的授权流程与各家 ROM 上 `queryEvents` 的实际返回**
  （事件类型、历史保留天数、数据延迟写入，厂商差异很大 ——
  这也是为什么推断层被设计成「只吃 raw int，不假设一定有哪些事件」）。

### 三条当前无法验证的事（避免误判完成度）

1. **Compose 布局无法由我目视验证。** 界面已经写出来，代码与状态映射都有测试钉着，
   但间距、换行、深色模式观感只有用户自己的眼睛能确认。现在已经连上真机（vivo / Android 16）
   并多轮试用，剩下的观感走查见 [`docs/DEVICE_CHECKLIST.md`](docs/DEVICE_CHECKLIST.md)。
2. **提醒的平台行为无法验证。** 见「模块 14」那一节：可行性最高的验证是「合并后的清单里
   接收器与权限都在」，而通知是否真的出现、闹钟是否按时触发只能上真机看。
3. **UsageStats 平台行为无法验证。** 权限授予流程（特殊权限，要跳系统设置）、
   各 ROM 的事件类型差异与历史保留策略，都需要真机
   （需求十六节第 11 条：先确认官方 API 行为再实现）。
   **已经做到的是**：把「事件怎么解释成记录」与「记录怎么写库」从平台层里彻底剥出来，
   用 674 个用例中的 118 个钉死了 —— 换到真机上需要验证的只剩
   「`queryEvents` 取回来的事件对不对」，而不是整条链路。

以上三条已逐条转成 [`docs/DEVICE_CHECKLIST.md`](docs/DEVICE_CHECKLIST.md) 里的可勾选动作。

上面三条的共同点是：**纯逻辑部分可以写、可以测；平台行为只能等真机**。
因此一直采用的做法是「把规则算清楚、把平台调用隔离在一层薄的适配器里」，
等有设备时只需要替换适配器，不需要推翻业务逻辑。
